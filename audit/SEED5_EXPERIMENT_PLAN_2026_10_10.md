## Four parallel workers

Use four independent Python processes in persistent remote tmux sessions. Separate processes isolate Python/NumPy/PyTorch random state. Each worker owns disjoint datasets and runs its list in order.

| Worker/session | Dataset queue, in order | Generator fits | Downstream runs | Reason |
| --- | --- | ---: | ---: | --- |
| `seed5-1` | MNIST28 | 4 | 53 | Start the expensive high-resolution fits immediately; keep shorter datasets out of this queue. |
| `seed5-2` | Covertype | 4 | 53 | Start this large population early so its long work does not accumulate at the end. Its lower feature width differs from the MNIST28 workload. |
| `seed5-3` | News → Census KDD | 8 | 90 | Start the smaller regression table beside the two larger datasets; defer the larger Census preparation/fits until News completes. |
| `seed5-4` | California Housing → Adult → MNIST12 | 12 | 143 | Start the smallest table, then Adult. Put MNIST12 last so both image-preparation pipelines do not start together. |
| Total | Seven datasets, seed 5 | 28 | 339 | Unequal run counts reflect unequal per-run costs. |

Each dataset follows the same maintained path: prepare/verify its fixed real partitions once; run the real-only baseline once; fit/sample independent full-table and X-only generators; create the applicable relabeled tables; train each construction under synthetic-only and mix. Preserve the saved full-table features when replacing its target. Save each X-only feature sample once so relabelers use a recorded feature source without repeatedly sampling a generator. Reuse those tables for both downstream training modes.

The initial four workers start **MNIST28, Covertype, News, and California Housing** together. This replaces the earlier four-heavy-dataset startup. It keeps two potentially long streams moving while allowing smaller tables to reach training as larger jobs prepare their inputs. Keep one subprocess active per worker. Start with two computation threads per native library pool (`OMP_NUM_THREADS=2`, `OPENBLAS_NUM_THREADS=2`, `MKL_NUM_THREADS=2`, inherited by every child). The installed environment check confirmed two threads in PyTorch, XGBoost, scikit-learn OpenMP, and NumPy/SciPy BLAS pools under those settings. This limits library parallelism; it is not CPU affinity or a hard limit on all threads in a process. The server has **four physical cores/eight logical CPUs** and one GTX 1080 Ti shared by all four workers.

### CPU/GPU allocation check

The installed versions are CTGAN **0.10.2**, SDV **1.18.0**, and RDT **1.13.2**. Reading their installed code, together with the main-source float32 transform correction, gives this division:

| Stage | CPU work | GPU work |
| --- | --- | --- |
| Source splitting, image resizing/grouping, encoding, SDV/CTGAN transformer fitting | Table preparation, one-hot encoding, and numerical-column mixture fitting | No generator training during this stage |
| CTGAN fitting | NumPy conditional/real-row sampling, batch transfers, and Python loops over column activations/losses | Generator/discriminator forward, backward, and optimizer work on CUDA |
| TVAE fitting | Transformer preparation, batching, Python column-loss loops, and synchronization for logged losses | Transformed training tensor, encoder, decoder, forward/backward, and optimizer work on CUDA |
| Synthetic sampling | Inverse transformation and CSV writing; CPU-side latent/condition preparation also occurs | Generator/decoder forward passes |
| Relabeling and downstream evaluation | NB, PCA/GMM, RF, and current CPU XGB; table loading/mixing | DNN labelers and downstream neural training |

Both MNIST variants prepare image rows on CPU. MNIST28 has 784 feature columns and MNIST12 has 144; numerous per-column Python/CUDA operations can make training host-sensitive despite CUDA being enabled. News and Housing also have CPU transformer/labeler phases, so a small dataset is not a dedicated GPU task. The existing sequential float32 transformer correction prevents the library's default parallel transformation/float64 memory expansion; preserve it rather than re-enabling joblib workers.

Saved manifest sizes support mixing workloads: MNIST28/MNIST12 each have 54,094 training rows; Covertype has 513,911, Census 162,962, News 28,543, Housing 14,861, and Adult 34,280. Raw feature widths are 784, 144, 54, 37, 58, 8, and 14 respectively. These are actual historical corrected manifests, not assumed split fractions or fitted timing estimates.

The proposed order is an inference intended to reduce coincident CPU preparation while keeping long tasks underway. Dataset order alone cannot guarantee complementary phases or continuous GPU occupancy. The exact four-worker seed-5 startup has not been benchmarked. Compare CPU use, epoch throughput, GPU utilization/memory, available RAM, and swap activity during the first production overlap; low GPU memory use alone does not identify the bottleneck. Do not add a dynamic scheduler, GPU locks, automatic retries, or change research budgets to chase a utilization percentage.
